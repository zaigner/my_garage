## Findings

### Defects

**R1. On `/estate/executor/`, "Remove" submits the Update form.** Disposition: **fix now.**
- *What's wrong:* `templates/my_garage/estate/executor.html:69-76` puts the Remove `<form>` inside the Update `<form>` (`:49-78`). Browsers drop a nested form start tag. Parsing the rendered page with html5lib, as a browser does, puts both the Update and Remove buttons in the `/estate/executor/` form.
- *Effect:* clicking Remove re-saves the executor and never deletes it. So 2.2's "removing the executor revokes the code" (`estate_views.py` `executor_remove`) can't be reached from the UI. The tests POST straight to the URL (`test_estate_story2_2.py:197`), so they pass anyway.
- *History:* the nesting dates from Epic 1 (`8390f82`). 2.2 (`d56c59b`) edited the confirm text inside it.
- *Prevention:* test which form a button actually belongs to in the rendered page, not only the endpoint.

**R2. The plaintext executor code waits in the owner's session until the success page is opened.** Disposition: **fix now.**
- *What's wrong:*
  - `estate_views.py:325` writes the raw code into the session, which this app stores in the database.
  - It's removed only when `estate_activate_success` (`:354`) is loaded.
  - That page has no `never_cache`, so a browser can show it again from cache.
  - The service docstring says the code "is never persisted" (`api/services.py:192`).
- *Effect:* if the redirect is never followed, a live code sits in `django_session` in clear text.
- *Prevention:* when a story handles a secret, its spec should say where the secret lives and for how long.

**R3. The only test that the success page shows the code can't fail.** Disposition: **fix now, together with R2.**
- *What's wrong:* `tests/functional/test_estate_story2_1.py:159` asserts `"estate" in content.lower() or len(content) > 100`, which any rendered page satisfies. No other test asserts that the code appears on the page.
- *Effect:* if a template change drops `{{ raw_token }}`, the owner sees a success page with no code, and the code can't be recovered.
- *Prevention:* check reviews for assertions joined with `or` that any page would satisfy.

**R4. The activation snapshot isn't linked to its token, and deleting an item deletes its snapshot.** Disposition: **defer; decide in correct-course.**
- *What's wrong:*
  - `ValuationSnapshot.item` is `on_delete=CASCADE` (`models.py:624-626`). That conflicts with FR39 ("cannot be modified or deleted after capture") and NFR17, even though the epic's own technical note asked for `CASCADE` (`epics-estate-legacy.md:475`).
  - Snapshots are matched to a token only by `created_at >= token.issued_at`, with no upper bound.
  - The portfolio and detail selectors break ties differently. `dict(values_list(...))` keeps the oldest row (`selectors.py:374-380`), while `.first()` keeps the newest (`selectors.py:439-444`).
- *Effect:*
  - Deleting an item after activation silently lowers the "value at activation" total.
  - If two activation snapshots ever exist for one item, the dashboard and the detail page show different values.

**R5. Once used, a code never expires.** Disposition: **defer; decide in correct-course.**
- *What's wrong:* `api/services.py:160-162` sets `expires_at=None` on first use. The code then works from any new browser until the owner revokes it.
- *Spec check:* this matches Story 2.2's AC ("the 72-hour window only applies to unused codes") and NFR7. But the epic intro says "one-time executor access code" (`epics-estate-legacy.md:431`), and the owner's success page says "expires after 72 hours if unused".
- *Decision needed:* whether a used code should stay valid forever.

**R6. Replacing the executor through Update leaves the old code live.** Disposition: **defer; decide in correct-course.**
- *What's wrong:* `estate_views.py:201-212` saves over the same `EstateExecutor` row.
- *Spec check:* the spec says editing details doesn't revoke (`epics-estate-legacy.md:561`), but the form can't tell a correction from a different person.

**R7. Soft-deleted collections are part of the estate.** Disposition: **defer; decide in correct-course.**
- *What's wrong:* activation (`api/services.py:208`), the executor portfolio (`selectors.py:369`), `get_executor_item` (`selectors.py:318`) and the owner's estate dashboard (`selectors.py:222`) all filter items by owner only. The rest of the app hides `CollectionType.is_active=False` (`views.py:133`).
- *Effect:* items in collections the owner deleted appear in totals and in the probate banner.

**R8. "Cost basis" and "Equity" at activation don't match the owner's figures.** Disposition: **defer; label decision.**
- *What's wrong:* the snapshot uses the raw `purchase_price` (`api/services.py:211-213`). That was a deliberate Story 2.1 choice, so a missing price stays null. Everywhere else, cost basis means `total_cost_basis` and equity is NFP.
- *Where it shows:* the 2.4 detail page labels these "Cost basis" and "Equity" (`item_detail.html:41-46`).

**R9. Page views crowd out security events on the owner's activity list.** Disposition: **defer.**
- *What's wrong:* the panel shows the last 10 log rows of any type (`selectors.py:271`). Stories 2.3 and 2.4 write one row per page view (`estate_views.py:115, :130`).
- *Effect:* ten clicks push `CODE_REJECTED` and `TOKEN_REVOKED` off the panel.

**R10. "In use — last used" shows when the code was entered, not when the portal was last used.** Disposition: **defer.**
- *What's wrong:* `last_used_at` is written only in `verify_executor_code` (`api/services.py:160-162`), but the 30-day session lets the executor browse without re-entering the code.

**R11. Negative money shows as positive outside equity.** Disposition: **defer, low.**
- *What's wrong:* `portal/_money.html:1` uses `currency_display`, which takes `abs()` (`templatetags/my_garage_extras.py:46`). Only snapshot equity was switched to a signed filter.

**R12. Estate timestamps render in UTC with no zone label.** Disposition: **defer, low.**
- *What's wrong:* `TIME_ZONE = "UTC"` (`config/settings/base.py:100`). The 72-hour expiry, the activity log, the activation date and valuation times all lack a zone label.

**R13. Deploy has no concurrency guard.** Disposition: **defer, low.**
- *What's wrong:* `.github/workflows/deploy.yml:5-27` has no `concurrency:` block.
- *Effect:* if two Builds finish out of order, the older image can be deployed last.

### Accepted as-is (recorded so later retros stop re-flagging them)

- **The Cloudflare Access bypass for `/estate/portal/*` was skipped** (user decision, 2026-10-26).
  - *Effect:* in production, an executor without an Access login can't reach the code-entry page, so FR16 works only on the LAN.
  - *Revisit when:* before handing a real code to anyone.
- **The access log fails closed.** The write happens after render with no guard (`estate_views.py:130`), so a failed write is a 500 rather than an unlogged view.
- **Code entry has no throttle, and unknown codes aren't logged** (`api/services.py:140-142`). The code is a 256-bit `token_urlsafe(32)`, so brute force isn't a practical risk.
- **Activation reads items outside the transaction and uses `date.today()`** (`api/services.py:207-208`). Neither has a realistic trigger for a single-owner app.
- **Two concurrent activations, or a double-submit,** could show a code that was already replaced. That needs a double-click inside one request's lifetime.
- **Beneficiary contact details aren't shown to the executor** (`selectors.py:324-341`). FR24 asks only for the name. This is a product question for later.
